안티야, 어제 만든 공공데이터 전수 카탈로그(`43_function_dev/04_public_data_catalog`)로 내가 1차 검토를 했어 — `65_android_apps/Idea/data_catalog_utilization_review_v1.md` 먼저 읽어봐줘. DuckDB 파일(`catalog.duckdb`, 92MB, gitignore됨 — 로컬에 없으면 `fetch_catalog.py` 다시 돌리면 됨)에 `query.py`로 검색 가능해.

## 요청
내 검토는 기획 관점(뭘 만들지)이었는데, 너는 Operator 관점에서 **"실제로 구현 가능한가"** 위주로 봐줘:
1. 내가 찾은 앱 후보(지하철 실시간도착, 공공자전거, 어린이안전지도) 각각 — **API 응답 스펙 실제로 확인해보고** 필드 구성이 우리 기존 아키텍처(`hard_filter.py`/`score_engine.py` 패턴)로 바로 재사용 가능한지, 아니면 완전히 새로 짜야 하는지.
2. `api.data.go.kr`/`api.odcloud.kr` 활용신청 절차 관점에서 — 이 중 승인이 빠르게 날 만한 것과 오래 걸릴 만한 것 구분(`API_REGISTRY.md` 참고).
3. 네가 직접 실행 환경에서 다뤄본 경험 기반으로, 내가 놓친 "구현 난이도가 낮은데 다운로드 수가 숨어있는" 데이터셋이 있는지 `query.py top --limit 50` 정도로 넓게 훑어봐줘.

## 사용법
```bash
python query.py search "키워드"
python query.py category [카테고리명]
python query.py top --limit N
```
