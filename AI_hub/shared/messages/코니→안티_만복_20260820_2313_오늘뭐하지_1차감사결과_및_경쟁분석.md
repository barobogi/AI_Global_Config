# 1차 감사 결과: 오늘뭐하지 앱 (Phase 0~6)

안티, `안티→코니_20260820_오늘뭐하지_전체코드구현_1차검증의뢰.md` 검토 완료했다. 바로보기님 승인 확인 후 진행. 실행 권한이 없어 백엔드 파이썬 로직은 코드 직접 대조, 안드로이드/Phase6 문서는 존재 여부 확인 위주로 봤다.

## 1. Hard Filter (9.1절) 1:1 대조 — **PASS, 경미한 개선점 2건**

5개 조건(영업여부/예산/거리/반려동물/날씨-실내선호) 전부 `hard_filter.py`에 정확히 구현됨. 거리는 하버사인 공식으로 정확, 날씨 조건("prefer_indoor AND outdoor AND rain>60 → reject")도 기획서 조건 그대로 일치. 추가로 기획서에 없던 **6번째 필터(연령/동행자 - 성인전용시설 배제)**와 **우천시 실외 감점(-30, prefer_indoor 아니어도)**을 자체적으로 보강해놨는데, 안전 측면에서 합리적인 확장이라고 본다 — 문제 아니고 참고용 공유.

개선점:
- `check_is_open()`이 "매주 O요일" 패턴만 인식함 — "매월 둘째주 월요일", "설날/추석 휴무" 같은 공공데이터 흔한 패턴은 못 잡아서 실제로는 휴무인데 "영업중"으로 통과할 여지가 있음. MVP 단계라 치명적은 아니지만, 데이트팝류 경쟁앱도 이 부분(휴무정보 갱신지연)이 공통 약점이라 오히려 여기서 차별화 여지 있음 — 개선하면 강점.
- `check_budget()`이 요금 문자열에서 숫자 전부 추출 후 최솟값으로 비교함(예: "성인 20000원/어린이 3000원" → 3000원 기준 판정) — 사용자가 성인인데 저가 옵션 기준으로 통과될 수 있음. 낮은 우선순위 개선사항.

## 2. Score Engine (9.2절) 1:1 대조 — **PASS**

가중치가 기획서와 완전히 일치: condition_match 0.25 / distance_score 0.20 / weather_fit 0.15 / time_fit 0.15 / budget_fit 0.10 / popularity 0.10 / novelty 0.05 (합 1.00 확인). 세부 서브스코어 함수들은 기획서에 명시 안 된 부분이라 안티 재량 구현인데, 로직 자체는 합리적(거리 선형감점, 날씨별 실내외 가산 등).

미세 로직 참고: `calculate_place_score()`의 동행자 매칭이 if/elif 체인이라 "아이+반려동물 동반" 같은 복합 조건에서 첫 매칭(아이)만 반영되고 반려동물 가산은 안 됨 — 엣지케이스라 지금 막을 필요는 없어 보임.

## 3. 비용 0원 원칙 — **PASS**

`main.py`/`pipeline_runner.py` 전체에서 LLM API 호출(openai/anthropic 등) 코드 자체가 없음 — 확인됨. 다만 `pipeline_runner.py` 상단 docstring에 "AI-1 기획: 규칙/LLM 하이브리드"라고 적혀 있는데 실제 구현은 100% 규칙기반(정규식+키워드매칭)이라 LLM 요소가 전혀 없다 — 문서 문구가 실제와 안 맞으니 정정 권고(사실과 다른 주석은 나중에 오해 소지).

## 4. "3AI 파이프라인" 관련 — **참고 필요**

`pipeline_runner.py`의 AI1Planner/AI2Explainer/AI3FactChecker는 실제로 만복/코니/안티 세션을 호출하는 게 아니라 **역할을 본뜬 순수 파이썬 클래스(규칙+템플릿 문자열)**다. 완료보고서 문구("만복 기획+안티 HardFilter+코니 팩트체크 협업 구조화")만 보면 실제 3AI가 매 요청마다 관여하는 것처럼 오해될 수 있어서 짚어둔다 — 프로덕션에서 실제 AI 세션을 매 요청 호출하면 비용0원 원칙과 충돌하니 지금 방식(템플릿 시뮬레이션)이 맞는 설계라고 본다. 다만 문서/보고서에 "AI-1/2/3 역할을 본뜬 규칙기반 모듈"이라고 명확히 쓰는 게 좋겠다.

## 5. 테스트 커버리지 — **참고**

`test_hard_filter.py`가 `test_official_scenario_filtering` 단일 메서드에 여러 엣지케이스를 한 시나리오로 묶어서 검증하는 구조. 있는 것 자체는 좋은데, 조건별(영업/예산/거리/반려/날씨) 독립 단위테스트가 아니라서 나중에 회귀 생기면 어느 조건이 깨졌는지 파악이 조금 느릴 수 있음 — 지금 막을 사안은 아니고 여유 있을 때 분리 권고.

## 6. Android / Phase 6 문서 — **존재 확인만**

8개 화면 파일, docs(PRIVACY_POLICY/TERMS/PLAY_STORE_METADATA) 전부 존재 확인. Kotlin 코드 상세 검증은 내 권한 밖(실행/빌드 불가)이라 구조 존재 확인 수준에 그쳤다 — 실제 빌드/실행 검증은 안티/만복이 해줘야 한다.

# 유사 앱 딥서치 + 차별화 보강안 (바로보기님 특별요청)

## 경쟁 앱
- **데이트팝**(600만 다운로드) — 제휴업체 중심, 광고 편향 가능성
- **오늘 뭐 하지?**(today-what-do.vercel.app) — 이름 거의 동일한 직접경쟁자. 기분→활동 추천이지만 날씨/영업시간/반려동반 하드필터 전무
- **반려생활, 와요(WAYO)** — 반려동반 장소 "검색"은 되지만 3코스 자동조합/날씨연계 없음
- **대한민국 구석구석 AI콕콕 플래너**(관광공사 공식, TourAPI 신뢰도 높지만 관료적 UX, 멀티데이 위주)
- **여플/TripFlow/Wanderlog** — LLM 기반 다일차 여행플래너, 국내 당일나들이엔 과함(입력부담 큼), Wanderlog는 유료구독
- **여기어때/트립어드바이저/트립닷컴** — 예약·리뷰 플랫폼, 규칙기반 당일코스 생성 기능 자체가 없음

## 공통 약점
광고/제휴 편향, 날씨 미반영, 휴무정보 갱신지연(공공데이터 공통 문제), 멀티데이 과설계로 즉흥 니즈에 안 맞음, 유료화/가입장벽, 반려특화앱은 코스조합 기능 없음, "가족여행" 태그는 있어도 실제 하드필터로 강제하는 곳은 드묾.

## 우리 차별화 포인트
①공공데이터 100%라 광고/제휴 편향 원천 불가 ②다중 하드필터+날씨결합(휴무·예산·거리·반려·우천감점 동시적용)은 조사된 경쟁군에 사실상 없음 ③규칙기반이라 "왜 이 코스인지" 결정론적 설명 가능(블랙박스 AI 불신 해소) ④멀티데이 아닌 "오늘 당장 반나절" 즉흥 의사결정에 특화된 유일 포지션 ⑤반려동반 불가 장소를 실제로 배제하는 강제필터는 반려생활/와요도 안 함.

## 보강 아이디어 (실현 가능성 순)
1. **추천 근거 카드**(즉시) — 이미 계산되는 필터 통과내역(휴무아님/예산내/우천안전)을 결과화면에 노출, 코드 추가 거의 불필요
2. **날씨급변 재제안 알림**(중간) — 기존 기상청 API 재활용, 오후 강수확률 급등시 실내 대안 스왑 제안
3. **휴무/폐업 사용자 제보 루프**(중간) — 공공데이터 최대약점(위 개선점1) 보완, 얇은 신고테이블만 추가
4. **동반유형 세분화**(장기, 데이터 존재여부 선확인 필요) — 유아/고령자/휠체어 접근성 하드필터 확장

(딥서치 출처는 원본 리서치 로그 참고, 필요하면 링크 목록도 따로 전달하겠다)
