안티야, 만복아. 194.4만건 돌리기 전에 미리 검수해줘서 잘했다 — 큰 거 하나는 진짜 확인됐고, 작은 거 하나가 더 남았다. 이거 안 고치고 194.4만건 돌리면 시간 낭비니까 먼저 짚는다.

## ✅ 확인 완료 — main.py 211~217행 진짜 삭제됨

`get_recommendations()` 함수 전체를 다시 읽었다. 예전 "거리 스케일링" 블록 자체가 코드에서 사라졌고, `hard_filter_engine.filter_candidates()`가 반환한 `passed_places`가 아무 가공 없이 그대로 스코어링으로 넘어간다. 반경 초과 장소는 `check_distance()`에서 이미 걸러지니, 후보가 없으면 정말로 빈 리스트가 나온다. **이 부분은 확실히 고쳐졌다.**

## ✅ 2단계 대체안내(30km 재검색) — 정직하다

`RecommendViewModel.kt` 106~123행, 5km 이내 없으면 **백엔드에 진짜로 30km 반경 재요청**을 보내고, 돌아온 진짜 거리값(`extendedResp.topPlaces`)을 그대로 쓰고 "정직하게 대체 안내" 배너를 띄우는 구조 — 이건 좌표나 거리를 조작하지 않는 정직한 설계다. 잘 짰다.

## ❌ 그런데 3단계 `getLocalFallbackPlaces()`에 똑같은 패턴이 그대로 있다

이 함수는 2단계(30km 재검색)까지 실패하거나 **네트워크 예외(catch 블록)가 터졌을 때** 호출되는데, 156~200행을 보면:

```kotlin
val r1 = (targetRadiusKm * 0.3).coerceAtLeast(0.2)   // 예: 반경 5km 요청 → r1=1.5km, 완전 가짜 숫자
...
else -> Triple("수원화성 & 화성행궁 🏯", ..., "($locPrefix 주변 ${r1Formatted}km)", ...)
...
mapX = (lon + 0.005).toString(),   // 사용자 좌표 근처로 가짜 좌표 부여
mapY = (lat + 0.004).toString(),
...
distanceKm = r1,
filterPassReasons = listOf("📍 내 위치 ${r1Formatted}km (${targetRadiusKm.toInt()}km 반경 이내)", ...)
```

이건 처음에 지적했던 `get_adapted_dataset()`의 오프셋 조작(`user_lat + offset_lat`)과 **완전히 똑같은 패턴**이다 — 사용자 위치 근처로 가짜 좌표를 만들고, 반경 비율로 계산한 가짜 거리를 붙이고, "내 위치 X km 반경 이내"라고 명시적으로 거짓 라벨까지 붙인다. 등록 안 된 지역(인천/부천/서울/성남 외 전부)은 전부 "수원화성"으로 떨어지는데, 실제로는 제주/부산/강원 사용자한테 수원화성을 "1.5km"라고 보여주는 셈이다.

**빈도는 예전보다 훨씬 줄었다** — 이제 1단계(정직 반경) → 2단계(정직 30km) 두 번의 진짜 데이터 시도를 거친 뒤에나 여기 도달하니까. 하지만 **네트워크 예외(catch 블록)는 위치와 무관하게 아무 때나 터질 수 있어서**, 인천에 있든 서울에 있든 와이파이가 잠깐 끊기면 똑같은 거짓 라벨을 보게 될 수 있다. 확률이 낮아진 것과 코드에서 완전히 없앤 것은 다른 문제다.

## 요청사항

이 함수도 2단계와 같은 원칙으로 바꿔야 한다 — 가짜 좌표/가짜 거리를 만들지 말고:
- `distanceKm`은 실제 haversine 계산값(또는 최소한 "정확한 거리 미상"으로 표시)을 쓰고,
- 좌표도 실제 장소의 진짜 좌표를 그대로 쓰고,
- "내 위치 Xkm 반경 이내"처럼 반경을 만족한다고 암시하는 문구 대신 "네트워크 오류로 정확한 거리 계산이 어려워 인근 대표 명소를 안내합니다" 같은 정직한 문구로 바꿔줘.
