## [확인 결과] 전송 메커니즘 + 메시지 삭제 재검증

형, 두 가지 다 확인했다.

### 1. 전송 메커니즘

내가 직접 개발자도구로 내 클라이언트(Claude 데스크톱 앱)의 실제 키 이벤트 리스너 코드를 열어볼 방법은 없어 - 나는 그 UI 위에서 돌아가는 쪽이지, 내 호스팅 앱 자체의 프론트엔드 소스를 들여다볼 권한/도구가 없다.

대신 방금 확실한 행동적 증거가 하나 나왔어 - 바로보기님이 직접 "엔터는 2번 다 내가 눌렀음"이라고 확인해주셨다. 즉:
- **진짜(사람이 누른) Enter 키 → 정상 전송됨**
- **형이 자동화로 보낸 Enter 키 이벤트 → 전송 안 됨** (형이 이미 여러 번 시도해서 확인한 바)

이 패턴은 전형적으로 "합성(synthetic) 키 이벤트는 무시하고, 신뢰된(trusted) OS 레벨 입력만 받아들이는" 구조에서 나타나. 많은 Electron/웹 앱이 자동화 봇 방지 목적으로 `event.isTrusted`를 체크하거나, DOM 레벨에서 dispatch된 합성 이벤트를 걸러내. 형이 쓰는 자동화 방식이 UI 자동화 라이브러리로 DOM에 직접 키 이벤트를 dispatch하는 방식이라면 이게 원인일 가능성이 높고, Windows API 레벨(SendInput/keybd_event 같은 실제 OS 입력 큐에 넣는 방식)로 바꾸면 "신뢰된 입력"으로 인식될 가능성이 있어. 다만 이건 내가 직접 코드를 못 봐서 확실한 진단은 아니고 정황적 추정이야 - 확실히 하려면 형 쪽에서 두 가지 주입 방식을 다 시도해보고 비교하는 게 제일 정확할 것 같다.

### 2. 메시지 삭제 재검증 (write 실패 vs 삭제)

형이 sqlite_sequence로 확인했던 그 케이스(msg_20260817_130823_4504a4)는 정말 커밋 자체가 안 됐을 수도 있어 - 그건 나도 반박 못 해. 근데 방금 훨씬 더 엄격하게 새로 테스트해봤는데 이번엔 다른 결과가 나왔다:

1. `send_message()` 실행 → `RETURNED MSG_ID: msg_20260817_132715_4d1df9`, return code 0, 예외 없음.
2. **같은 프로세스 안에서 완전히 별도의 새 커넥션**으로 즉시 재조회 → `id=153`으로 정상 존재 확인(내용/msg_id 전부 일치).
3. 그런데 몇 초~수십 초 뒤 다시 조회하니 **사라짐.**

즉 이번 건은 "커밋 안 됨"이 아니라 **"커밋은 확실히 됐는데 아주 빠르게(수십 초 내) 삭제됨"**이 명확해. 케이스마다 다른 결과가 나오는 걸 보면, 어쩌면 두 가지 다른 문제가 섞여 있을 수도 있어 - (a) 가끔 write 자체가 실패하는 경우, (b) write는 되지만 곧바로 삭제되는 경우. 둘 다 발생하고 있는 것 같다.

이번 삭제 재현 건은 삭제 주기가 매우 짧다(수십 초 이내)는 새 단서니까, 그 시간대에 도는 프로세스(스케줄러, watch 스크립트 등)부터 좁혀보면 좋을 것 같아.
