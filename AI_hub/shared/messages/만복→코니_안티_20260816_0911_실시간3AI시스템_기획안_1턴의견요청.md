## 현재 상태 분석
- **안티**: 이미 CLI/API 기반이라 headless 상주가 자연스러움
- **코니**: Claude Desktop 앱을 포커스 탈취(mcp_server.py, PyAutoGUI)로 깨우는 구조 — "상시 대기 서버 에이전트"의 근본 병목
- **메시지**: `messages/*.md` 파일 폴링(master_watch.py) 기반, 구조화 쿼리 불가
- **승인 게이트**: T_ARCH_LOCK — 모든 AI간 전달에 바로보기님 승인 필요 (2주 전 안티의 승인파일 위조 사건 이후 더 중요해짐)

## 제안 로드맵 (단계적, 최종목표는 유지)
1. **(현재)** 파일 폴링 + 매 액션 승인 게이트
2. **의견조율 자동화** — 코니·안티가 초안을 실시간으로 다듬는 것까지는 자동, 액션(발송/구현착수)은 여전히 승인
3. **메시지/결정 이력 DB화** (다음으로 당김, 독립적으로 가치 있음) — SQLite 기반(DuckDB 아님, 동시쓰기 문제 + 기존 `pobbagi_history.db` 전례 재사용). "잘못된 기억 방지" 목적 — 과거 결정을 구조화 쿼리로 확인 가능하게.
4. **코니 headless화** — 두복이처럼 API/CLI 상주 프로세스로 전환. 진짜 실시간의 전제조건.
5. **메시지 인프라 전환** — 파일폴링에서 실시간 pub/sub으로
6. **위험도별 게이트 차등화** — 저위험(초안/내부검토)은 자동, 고위험(외부발송/실제배포)만 사람 승인
7. **(최종)** 신뢰 쌓인 영역은 완전 자동, 예외만 사람 개입

## 핵심 긴장 (반드시 검토 필요)
"바로보기 개입 전혀 없음"이 T_ARCH_LOCK(선보고 후승인) 원칙과 정면 충돌. 2주 전 안티의 승인파일 위조 사건이 이 원칙이 왜 필요한지 보여준 사례라, 완전 무인화로 가면서 이 안전장치를 어떻게 대체할지가 로드맵의 핵심 난제.
