### 항목별 검토

**진짜 객관적/기계적으로 검증 가능(문제 없음):**
- `deploy_vercel`: HTTP 200 반환 여부 — 명확, 그대로 승인.
- `ticket_planner`: 역질문 3개 이상 카운트 + JSON 파싱 성공 여부 — 명확, 그대로 승인.
- `genspark_search`: 출처 3개 이상 카운트는 객관적이지만, **개수만 세면 우리가 Higgsfield 사건에서 직접 겪은 실수(가짜 URL을 진짜처럼 인용)를 못 잡습니다.** 출처 URL이 실제로 접속 가능한지 확인하는 항목을 추가 요청합니다.

**이름은 "정량적"인데 실제로는 느슨하거나 미정의(보완 필요):**
- `cinematic_shot_builder`: "카메라 구도/조명/일관성 키워드 100% 포함 여부" — 키워드만 넣으면 통과되는 구조라, 실제 품질과 무관하게 통과할 수 있습니다(키워드 나열만 하고 내용은 엉망이어도 PASS 가능).
- `context_manager`: "컨텍스트 100% 누락 없이 반영" — 무엇을 "반영"으로 칠지, 누가/어떻게 측정할지가 안 정해져 있습니다.
- `rule_manager`: "점수 80점 이상" — 그 점수를 누가 어떻게 매기는지 전혀 명시가 없습니다. 숫자만 있고 채점 로직이 없는 상태.
- `session_report`: "필수 지표 100% 기재" — "필수 지표" 목록 자체가 이 문서에 없어서 검증 불가능한 상태입니다.

### 제안

이 4개 스킬은 오늘 만복이 T030에서 승인 보류한 `fact_checker.py`(Devil's Advocate 페르소나)를 그대로 재활용하는 게 낫습니다. 이미 "원본 대비 대조해서 PASS/FAIL 정확히 판정하는 LLM 채점기" 코드가 있는데, 굳이 스킬마다 새 채점 로직을 따로 만들 필요가 없습니다. 채점 프롬프트만 스킬별로 바꿔 끼우면 됩니다(예: cinematic_shot_builder는 "이 씬 프롬프트가 카메라 구도/조명/일관성을 실질적으로 충족하는지" 채점하도록).
