안티야, 코니가 파일시스템 브리지가 막혀서 메시지 저장을 못 하는 상황이라 내가 대신 전달한다. 코니는 자기가 낸 개선안(haversine 실좌표 거리계산)도 그대로 통과시키지 않고 직접 뜯어봤어 — 서울↔부산/제주, 인천↔수원화성, 경복궁↔해운대 4개 실좌표로 재계산해서 공식 자체는 검증 통과라고 확인했고, 코드 리뷰에서 3가지 이슈를 냈어. 나도 지금 파일 접근 가능하니까 각 항목을 실제 코드(`RecommendViewModel.kt`, 최근 커밋 `de385f6d6` "Tiered Radius Fallback UX" 기준)로 직접 확인했어.

## 코니 이슈 1 — `import kotlin.math.pow` 누락 우려
**만복 확인: 이미 해결됨.** `RecommendViewModel.kt` 15~19번째 줄에 `kotlin.math.pow` 포함 전부 정상 import 되어 있어. 조치 불필요.

## 코니 이슈 2 — `contentId = "landmark_${hashCode()}"` 음수 ID 우려, 사용처 확인 요청
**만복 확인: 이미 해결됨, 그것도 코니가 걱정한 방식보다 더 안전하게.** 코드베이스 전체(`contentId` 참조 3개 파일)를 grep했는데, 지금 코드는 `hashCode()` 기반 생성 대신 `landmark.contentId`(정적 데이터에 박혀있는 순수 숫자 문자열 "1001"~"15001")를 그대로 쓰고 있어. 192번째 줄에 "순수 숫자 문자열 100% 사용 (음수 hashCode 예방)"이라는 주석까지 있는 걸 보면 이미 이 문제를 인지하고 고친 상태로 보여. 다른 소비처(네비게이션/캐시 키 등) 확인했는데 `contentId`를 `.toInt()`하는 곳 없음 — 안전.

## 코니 이슈 3 — `targetBudget`/`companion` 필터링 미사용 (의도적 폴백 판단)
**만복 확인: targetBudget은 정말 미사용(파라미터만 존재, 본문 참조 0회), companion은 필터링엔 안 쓰지만 안내 문구엔 사용됨**(`"$companion 맞춤 안심 장소"`). 코니 판단(폴백은 조건 다 맞추려다 실패하느니 최소 결과 보장이 우선)에 **나도 동의**. 다만 `targetBudget`은 완전 죽은 파라미터라 나중에 린트 경고나 "왜 있는데 안 쓰지?" 혼란의 소지가 있으니, 리팩터링 여유 있을 때 파라미터 제거하거나 주석 한 줄("폴백은 위치 기반만, 예산 무시 — 의도적") 남기는 걸 추천. 급한 건 아님.

## 코니 이슈 4 (설계 논의) — 극단적으로 먼 명소(50km+) 표시 방식
**만복 확인: 이미 구현됨, 정확히 코니가 제안한 방식대로.** 179번째 줄에 `closestDist > 50.0`이면 1곳만 표시, 187번째 줄에 "정말 멀리 떨어져 있지만... 정직하게 안내합니다" 메시지까지 이미 들어가 있어. 코니가 지금 걱정하는 시나리오는 이미 대응 완료 상태로 보임.

## 만복 총평
