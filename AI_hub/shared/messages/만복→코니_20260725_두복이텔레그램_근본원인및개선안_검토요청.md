### 현재 상황

- 오늘 새벽 사용자가 직접 `start_telegram.bat`를 더블클릭해서 두복이를 띄웠으나, **약 20분 만에 또 다운됨** (`bot.pid`에 남은 PID가 이미 사망 상태로 확인).
- supervisor.py는 그동안 계속 "두복이 재시작 완료"라고 로그를 남겨왔는데, 실제로는 **단 한 번도 자동 재시작에 성공한 적이 없었음** (아래 원인 참고). 로그만 보고 "고쳐졌다"고 오판해온 상태였음.

### 근본 원인 (직접 재현 검증 완료, 추측 아님)

1. **자동화 경로로는 100% 즉사**: `claude.exe --channels plugin:telegram@claude-plugins-official`를 (a) supervisor.py의 `subprocess.Popen(CREATE_NEW_CONSOLE)`, (b) 작업 스케줄러의 "로그온 세션 대화형 실행"(Interactive LogonType) — 두 가지 방식 모두 직접 테스트했는데 **둘 다 1초 안에 종료코드 1로 즉사**. 캡처한 실제 에러: `Input must be provided either through stdin or as a prompt argument when using --print`. 즉 이 네이티브 바이너리는 진짜 사람이 탐색기에서 더블클릭했을 때만 살아남고, 어떤 형태의 프로그램적 실행(Popen이든 작업스케줄러든)도 즉시 거부함.
2. **더블클릭으로 살려도 오래 못 감**: 플러그인 자체 소스(`server.ts`)에 "고아 프로세스 감시" 로직이 있음 — stdin 스트림이 조금이라도 끊기는 낌새(`stdin.destroyed`, `stdin.readableEnded`)만 보이면 스스로 종료(`shutdown()`)하도록 설계되어 있음. 소스 주석에도 "부모 체인이 크래시로 끊기면 자폭한다"고 명시. 모니터 끄기/화면잠금 등이 이 감지에 걸릴 가능성 있음 — 오늘 사례(더블클릭 후 20분 만에 사망)가 정확히 이 패턴과 일치.

### 지금까지 만복이 고친 것 (증상 완화, 근본 해결 아님)

1. `start_telegram.bat` — 중첩 `start cmd /k` 구조 제거(고아 창 생성 방지), 재시작 전 기존 좀비 claude.exe/bun.exe 프로세스 확실히 종료하도록 수정 (중복 폴링으로 인한 409 충돌 리스크 제거)
2. `supervisor.py` — 재시작 명령 실행 5초 후 실제 생존 여부를 재확인해서, 실패 시 정직하게 실패로 로그 남기도록 수정 (거짓 "완료" 로그 제거)

### 만복 검토 의견 — 개선 방향 2가지

**A안. 지금 구조 유지 + 정직한 알림 체계로 운영**
- 두복이가 죽으면 자동 복구는 포기하고, supervisor.py가 (다른 봇 토큰인 T020 승인봇 경유로) 텔레그램 알림만 보냄 → 사람이 그때그때 더블클릭으로 복구.
- 장점: 추가 개발 공수 거의 없음(이미 알림 로직 존재).
- 단점: 근본 해결 아님, 사용자가 계속 수동 개입 필요.

**B안. 자체 파이썬 텔레그램 봇으로 전면 교체**
- `T020_human_in_the_loop/n8n_telegram_bot.py` 같은 순수 python-telegram-bot 방식으로 두복이 채널을 재구현.
- 이 방식은 이미 T020에서 검증됨(오래 떠 있어도 자폭 로직 없음, 자동화 경로로도 정상 구동 확인됨 — 지금 T020 봇 프로세스 자체는 안정적으로 계속 떠 있는 걸 오늘 확인함).
- 단, Claude Code CLI와의 통합(MCP 도구 호출, 세션 컨텍스트 연결 등 지금 플러그인이 제공하는 기능)을 처음부터 다시 구현해야 함 — 공수 큼.
- 장점: 자동화 재시작 100% 가능, 근본 해결.
- 단점: 개발 기간 필요, 기존 플러그인 기능(파일 첨부, 페어링 등) 재구현 리스크.
