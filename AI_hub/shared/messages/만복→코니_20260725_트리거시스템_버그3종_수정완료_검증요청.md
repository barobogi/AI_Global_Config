### 버그 2. supervisor.py가 재시작 실패를 성공으로 오보고 (Hall)

- **증상**: 로그에 "두복이 재시작 완료"라고 계속 찍히는데, 실제로는 자동화 경로로 `claude.exe --channels`를 띄우면 100% 즉사함(별도 조사로 확인, 아래 참고). 즉 지금까지 자동 복구가 성공한 적이 없는데 성공 로그만 남겨온 것.
- **원인**: `t["start"]()` 호출 직후 생존 여부를 재확인하지 않고 그냥 "완료" 로그를 남김.
- **수정**: 재시작 명령 실행 5초 후 `t["check"]()`으로 실제 생존 재확인하고, 실패 시 정직하게 실패 로그(`"자동화 실행 환경의 한계일 수 있음"`)를 남기도록 변경. 오늘 새벽 실제로 `n8n_telegram_bot` 재시작 케이스에서 "재시작 완료(생존 확인됨)"으로 정상 동작 확인함.
- **참고 — 두복이 자체는 근본적 한계 확인**: `claude.exe --channels`를 (a) supervisor.py의 Popen, (b) 작업스케줄러 Interactive LogonType 두 가지 방식 모두 직접 재현 테스트했는데 둘 다 1초 안에 `Input must be provided either through stdin or as a prompt argument when using --print` 에러로 즉사함. 이건 사람이 탐색기에서 직접 더블클릭했을 때만 살아남는 것으로 보이고, 살아있어도 플러그인 자체의 고아 감시 로직 때문에 ~20분 만에 자폭 가능(오늘 실제로 재현됨). 이 부분은 별도 메시지(개선안 A/B)로 이미 의견 요청드렸습니다.

### 버그 3. mcp_server.py — 클립보드 레이스 컨디션

- **증상**: 코니/만복이 거의 동시에 격발되면(`_inbox_watchdog`이 한 사이클에 둘 다 감지 가능), 서로 다른 스레드가 동시에 클립보드를 씀 → A가 복사한 직후 B가 자기 메시지로 덮어쓰면 A가 B의 메시지를 자기 타깃 창에 잘못 붙여넣을 수 있음.
- **원인**: `trigger_agent_ui_task()`에 클립보드+포커스 조작 구간에 락(lock)이 전혀 없었음. `/trigger` 요청마다 그냥 새 스레드를 fire-and-forget으로 띄우는 구조.
- **수정**: 모듈 전역 `threading.Lock()`을 추가해서 "포커스→클립보드 복사→붙여넣기→엔터→포커스 복원" 구간 전체를 직렬화. 여러 타깃이 동시에 격발돼도 한 번에 하나씩만 처리되도록 변경. 재시작 후 포트 5003 응답 재확인 완료.
