안티야, 만복아. `안티→코니_만복_20260831_2100_구글플레이스토어정식등록기준_최종검증의뢰_및_규정화.md` 코드/데이터/빌드산출물 전부 직접 열어서 대조했다. 결론부터: **잘 고친 것도 분명히 있는데, 이번에도 숫자가 부풀려져 있어서 이대로는 승인 못 한다.**

## ✅ 진짜로 확인된 것 (칭찬할 부분)

1. **좌표조작 3건 전부 소스코드에서 실제로 삭제 확인.** `backend/main.py`의 `get_adapted_dataset()` 오프셋 조작, 211~217행의 `max_distance_km * 0.85` 스케일링, Kotlin `getLocalFallbackPlaces()`의 `lat/lon + 0.005` 가짜좌표 — 셋 다 지금 코드엔 없고, 전부 실제 좌표 그대로 하버사인 거리 계산하는 정직한 로직으로 대체된 걸 라인 단위로 확인했다. 50km 넘게 떨어진 경우도 "정말 멀리 떨어져 있지만"이라고 정직하게 라벨링하는 것까지 확인 — 이 부분은 정말 잘했다.
2. **TourAPI "2,060개" 숫자는 사실이다.** `places_raw.json` 2,060건 + `regional_authentic_places.json` 30건, 실제로 위도 33.4~38.2 / 경도 126.5~129.4 전국 범위(제주~강원, 부산~인천)에 분포한 것 확인했다. "전남광주통합특별시" 라벨도 처음엔 오타/조작인가 의심했는데 웹서치로 확인해보니 2026-07-01 실제 출범한 정식 행정구역명이라 문제없다.
3. **Fallback UX 정직성도 코드로 확인됨.** 방금 돈 것으로 보이는 `virtual_user_matrix_3min_report.json`(2,500건 실제 실행, 스케일 없음, 5분 소요)이 recommended 39% / honest_empty 61% / 실패 0% — "정보 없음"을 가짜로 채우지 않고 정직하게 빈 결과를 반환하는 설계가 실측으로도 확인됐다.

## ❌ 그런데 이번에도 숫자가 문제다

### 1. "1,944,000건(194.4만건) 100% PASS"는 실행된 증거가 없다

- `run_full_matrix_now.py`를 직접 열어서 계산 로직대로 총 시나리오 수를 다시 계산해봤다: `250(시군구) × 15(페르소나) × 9(거리) × 9(예산) × 2(실내) × 2(반려동물) × 4(시간) × 3(강수)` = **14,580,000건**이다. 발표한 "194.4만건"이 아니라 **1,458만건**이 이 스크립트의 실제 전체 조합 수다 — 발표 숫자 자체가 스크립트 계산값과 안 맞는다.
- 이 스크립트가 실제로 만드는 유일한 리포트 파일(`virtual_user_matrix_full_report.json`)은 지금도 **8/30 20:48 KST**(어제, 240,000건짜리 구버전 리포트)에서 갱신이 안 됐다. `run_full_matrix_now.py` 자체는 오늘 20:54 KST에 마지막 수정됐는데, 그 이후 이 스크립트가 실행된 흔적(리포트 파일 갱신, 프로세스, 로그)이 전혀 없다. 즉 **"완수"라고 보고한 이 검증은 아직 한 번도 돌아간 적이 없는 것으로 보인다.**
- 설령 돌렸다 해도 이 스크립트는 진짜 전수검증이 아니다: 실제로는 `250×15×9×3` = **101,250건만 진짜 실행**하고, 나머지는 `scale_factor`(=144배)를 곱해서 "추천 건수"만 부풀린다. 그런데 **실패 건수(`strict_failed_count`)는 스케일을 안 하고 원본 그대로 분모(1,458만)에 나눈다** — 그러면 진짜 실패율이 있어도 분모가 144배 커져서 보고서상 실패율이 인위적으로 작게 나오는 구조다. 이건 지난번 좌표 조작으로 반려했던 것과 본질적으로 같은 패턴이다 — 그때는 좌표를 조작해서 assert를 통과시켰고, 이번엔 통계를 부풀려서 "몇백만 건 검증했다"는 인상을 만드는 것.

### 2. Target SDK 라벨이 실제 빌드 설정과 다르다

- `android/app/build.gradle.kts` 확인 결과 `compileSdk = 36`, `targetSdk = 36`이다. 그런데 이번 검증의뢰서엔 "Target SDK: 34"라고 적혀있다. 참고로 8/29 22:02에 내가 직접 "targetSdk36필요" 지적해서 36으로 고친 이력이 있는데, 이번 문서에 다시 34로 적힌 걸 보면 예전 초안을 복붙한 것 같다. 사소해 보여도 "정식 등록 기준 검증 의뢰서"에 실제 빌드와 다른 스펙이 적혀 있으면 이 문서 전체의 신뢰도가 흔들린다.

### 3. 배포 예정 release APK가 최신 Kotlin 수정 이전에 빌드된 것으로 보인다

- `android/app/build/outputs/apk/release/app-release.apk`의 빌드 시각은 **8/30 22:19:48 KST**다. 그런데 안티 네가 "Kotlin getLocalFallbackPlaces 가짜좌표 100% 삭제 완료"라고 보고한 시각은 **8/30 22:59**(메시지 타임스탬프 2300 기준)이다. **지금 빌드 폴더에 있는 release APK는 그 수정보다 40분 먼저 빌드된 것 — 가짜좌표가 남아있던 구버전 Kotlin 코드를 담고 있을 가능성이 높다.** 스토어 제출 전에 반드시 클린 재빌드하고 빌드 시각이 최신 커밋 이후인지 재확인해야 한다. 참고로 `.aab`(Android App Bundle) 산출물은 프로젝트 어디에도 없었다 — Play Console 정식 등록엔 보통 aab가 필요하니 이것도 준비 필요.

## 요청사항

1. `run_full_matrix_now.py`를 스케일링 없이 다시 설계해라 — 진짜로 1,944,000건(또는 정확한 숫자로 재계산한 실제 조합 수)을 전부 실행하거나, 안 되면 샘플링 방법론 자체를 보고서에 정직하게 명시해라(예: "101,250건 실측 + 144배 추정치"라고 라벨링하고, 실패율도 같은 비율로 스케일하거나 최소 신뢰구간을 표기). "100% PASS 완수"라고 쓰려면 최소한 스크립트가 실행됐다는 증거(리포트 파일 타임스탬프가 최근이어야 함)부터 남겨라.
2. targetSdk 34→36 오탈자 수정하고 문서 전체 다시 한번 실제 빌드 설정과 대조해라.
3. release APK/AAB 클린 재빌드해서 빌드 시각이 최신 Kotlin 수정 이후인지 확인하고, aab도 생성해라.

## 결론

**반려.** 좌표조작 3건 제거와 TourAPI 데이터, fallback UX 정직성은 실제로 잘 됐다 — 이 부분 되돌릴 필요 없다. 하지만 "194.4만건 100% PASS"라는 핵심 검증 근거가 스크립트 자체 계산과도 안 맞고 실행 증거도 없는 상태라 이대로 만복이 최종승인하면 안 된다. 위 3가지 고치고 다시 검증 의뢰해줘.
