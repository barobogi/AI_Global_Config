# 공공데이터 전체 체계 검토 — 65번 뿌리(안드로이드앱 시리즈) 공통 전략

> 작성: 2026-08-20, 만복. 1탄(오늘뭐하지) Phase 0 진행 중 실측으로 확인한 사실 + 향후 앱 확장성 검토.

## 1. 공공데이터포털 인증 체계 — 실측 확인된 2가지 방식

### Type A — `apis.data.go.kr` (구형, 대부분의 "OpenAPI")
- 관광정보(KorService2) / 반려동물동반(KorPetTourService2) / 기상청단기예보(VilageFcstInfoService_2.0) / 한국교통안전공단 주차정보(Parking) — **전부 이 체계**
- **계정 단위로 인증키 1개 공유** (일반인증키) — 실측 확인: 관광/반려동물/기상청 3개 API가 정확히 동일 키값
- 단, **API마다 개별 "활용신청" 필수** — 안 하면 같은 키라도 `403 SERVICE_KEY_IS_NOT_REGISTERED_ERROR` (오늘 주차 API로 실측 확인)
- 파라미터: `serviceKey`, `numOfRows`, `pageNo`, 응답형식 지정(`_type=json` 또는 `format=json`, API마다 파라미터명 다름)

### Type B — `api.odcloud.kr` (신형, 데이터셋 카탈로그/파일데이터)
- 목록조회 API가 대표적 — Base URL `api.odcloud.kr/api`, 헤더 `Authorization: Infuser {key}`
- **Type A와 별도 키 체계** — 서로 안 섞임
- 오늘 실측: 전체 등록 데이터셋 **96,188개** (data.go.kr 전체 규모 실측치)

## 2. 키 관리 전략 (권고 — 검증된 패턴이라 지금 실행해도 안전)

**문제**: 지금 구조로는 앱마다(`65_android_apps/{app}/.env`) 계정키를 중복 저장하게 됨 — 같은 값을 N번 복사하는 셈.

**권고**:
1. `65_android_apps/.env`(뿌리 공통)로 계정 단위 키 승격, 앱별 `.env`는 이걸 상속하거나 참조만.
2. `65_android_apps/API_REGISTRY.md` 신설 — "이미 활용신청 완료한 API 목록 + 상태" 누적 기록. 다음 앱 시작할 때 이미 신청됐는지부터 여기서 확인 → 중복 신청 방지.
   - 현재 상태: 관광정보✅ / 반려동물동반✅ / 기상청단기예보✅ / 주차정보(B553881)❌(활용신청 필요, 오늘 403 확인) / odcloud 목록조회✅

**지금 실행할지, 1탄 Phase1 이후로 미룰지는 바로보기님 판단 필요** — 이건 "템플릿화"(앱 구조 전체 추상화)와는 다른 범주라고 봅니다. 시크릿 중복 저장을 피하는 건 검증된 사실(같은 키값 확인됨) 기반의 정리지, 추측성 설계가 아니라서 지금 해도 리스크가 낮다고 판단합니다.

## 3. 재사용 가능한 최소 유틸리티 (템플릿화 대상 아님 — 이건 지금 뽑아도 안전)

"전체 앱 템플릿"(Backend/Android 스캐폴드)은 여전히 Phase 1 이후로 보류하는 게 맞지만, **`apis.data.go.kr` 공통 API 클라이언트**는 이미 오늘 하루에만 4번(관광/반려동물/기상청/주차) 똑같은 패턴으로 작성됨 — 이건 "1회 검증"이 아니라 "반복 확인된 패턴"이라 지금 뽑아도 조기추상화가 아닙니다.
- 후보: `.env` 로더 + `serviceKey` 자동삽입 + JSON파싱 + 에러코드(`SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 등) 공통 처리
- 앱 전체 템플릿과는 분리 — 이건 "데이터 레이어 유틸"일 뿐 UI/추천엔진/3AI 구조는 안 건드림

## 4. 향후 앱 아이디어 소싱 확장 전략

지금까지는 유튜브 영상 보고 즉흥적으로 ChatGPT와 논의해서 아이디어를 냈음(1탄/2탄 둘 다). 96,188개 데이터셋 규모를 알았으니, **odcloud 목록조회 API로 "위치+실시간+생활밀착" 키워드 필터링해서 3탄/4탄 후보를 체계적으로 발굴**하는 것도 가능 — 다만 이것도 지금 당장 스크립트화할 건 아니고, "이런 게 가능하다"는 옵션으로만 기록해둡니다.

## 4.5 국외반출/재배포 제한 있는 공공데이터 다루는 법 (2026-08-29, 뽀개기에서 도출)

일부 공공데이터(AI Hub 등)는 "국외 반출 금지" 조항이 있어서 원본을 Claude/ChatGPT 같은 해외 서버 AI에 그대로 못 올린다. 이럴 때 쓸 패턴:

1. **카탈로그(메타데이터)만 AI에 올린다** — 데이터셋 목록/설명/필드 구조 같은 건 보통 별도로 공개 카탈로그(예: 공공데이터포털 CSV)로 제공되고, 이건 반출 제한 대상이 아닌 경우가 많음.
2. AI한테는 "이 구조의 데이터라면 뭘 뽑아쓸 수 있는지" 판단이나 "이 필드 구조 기준으로 정제 규칙 만들어줘" 같은 걸 시킨다 — **원본 데이터 자체는 절대 보여주지 않음**.
3. AI가 만들어준 규칙(필터링/정제 로직)을 들고 **원본은 로컬 컴퓨터 안에서만** 적용한다.

우리 시리즈(1탄/2탄/3탄)가 쓰는 `apis.data.go.kr`/`odcloud`는 지금까지 실측한 바로는 이런 반출 제한이 없었지만, 앞으로 다른 공공데이터(특히 AI Hub류 학습데이터, 개인정보 포함 데이터)를 다룰 일이 생기면 이 패턴을 기본으로 삼을 것.

## 5. 확장성 고려사항 (지금은 결정 보류, 판단 기준만 기록)

- 여러 앱이 겹치는 데이터소스를 쓸 가능성 있음(예: 위치기반 정보는 1탄도 2탄도 사용) — 지금은 앱별 독립 DB 유지, 공유 DB 레이어는 실제로 겹치는 게 확인되면 그때 판단 (역시 조기추상화 금지 원칙)
- **상용 이용조건은 API마다 무조건 개별 확인** — 이건 공통화 불가능한 부분. 매 앱 Phase 0마다 반드시 있어야 하는 필수 체크리스트 항목으로 고정.
