# 빈자리 있어요? — 최종 기획서

## 1. 제품 정의
**지금 이 순간, 걸어갈 수 있는 거리 안에서 자리 있는 도서관/열람실을 알려주는 앱.**

만복이 V1의 Lean 원칙과 단일 킬러피처를 그대로 유지한다. V1은 잔여좌석 0 제외, 잔여좌석순/거리순 토글, 마지막 갱신시각을 핵심 출력으로 정의했다. fileciteturn2file0L11-L21

## 2. 핵심 사용자 문제
- 도서관에 도착했는데 자리가 없어 헛걸음한다.
- 여러 도서관의 좌석 상태를 각각 확인해야 한다.
- 만석 정보보다 “지금 어디에 빈자리가 있는가”가 중요하다. fileciteturn2file4L353-L361

## 3. 핵심 데이터
행정안전부/한국지역정보개발원의 `B551982/plr_v2`는 공공도서관 열람실 실시간 정보 API로 공개되어 있으며, 공식 안내에서도 `info_v2`, `rlt_rdrm_info_v2`, `prst_info_v2` 계열이 확인된다. citeturn0search0

V1 문서에는 활용신청 완료 상태가 기록되어 있고, 도서관명·열람실명·총좌석·이용좌석·잔여좌석·좌표는 **추정 필드이며 Phase 0 실측 확인이 필요**하다고 명시되어 있다. fileciteturn2file4L363-L367

따라서 최종 코드에는 확인하지 않은 필드를 사실처럼 고정하지 않고 **B551982 Adapter**를 둔다.

## 4. 킬러 피처
딱 하나:
> **주변에서 지금 빈자리가 있는 열람실을 찾는다.**

예:
```text
A도서관 3층 열람실
잔여 12석 / 총 80석
도보 8분
```
V1의 정의를 그대로 계승한다. fileciteturn2file4L369-L375

## 5. 추천 로직
입력: 현재 위치 + 최대 도보시간.

1. 범위 내 도서관 필터
2. 잔여좌석 0 제외
3. `빈자리 많은 순` 또는 `가까운 순` 정렬
4. 잔여/총좌석 + 거리/도보시간 + 마지막 갱신시각 출력

가중합 점수는 넣지 않는다. fileciteturn2file0L11-L21

### 의도적으로 제외

이는 V1의 Lean 범위와 동일하다. fileciteturn2file1L49-L62

## 7. 실제 API 연동 전략
공공데이터 Open API는 인증키 발급 및 활용신청/승인이 필요하므로 키는 앱에 직접 넣지 않고 서버 환경변수/Secret Manager에서 관리한다. citeturn0search4

### Phase 0 — 필수 검증
- 실제 `B551982/plr_v2` 응답 호출
- 실제 endpoint/operation 확인
- JSON/XML 응답 구조 확인
- 필드명 확정
- 좌표 존재 여부 확인
- 갱신시각/갱신주기 확인
- 지역별 데이터 편차 확인
- 이용허락/상업적 이용/캐싱 조건 확인

현재 환경에서는 사용자의 실제 승인키가 제공되지 않았으므로 **실제 API를 호출했다고 가장하지 않는다.** ZIP은 실측 직후 교체할 수 있도록 Adapter와 계약을 완성해 둔다.

## 8. 데이터 신뢰 UX
“실시간”이라는 문구만 강조하지 않는다.

예:
- `2분 전 확인`
- `12분 전 확인`
- `데이터 확인 불가`

오래된 데이터는 숨기지 않고 표시한다.

## 10. 상용화 구조
```text
Android
   ↓
Backend API
   ↓
Cache / SQLite
   ↓
B551982 Adapter
   ↓
공공데이터 API
```

초기에는 SQLite로 시작하고 트래픽 증가 후 PostgreSQL/Redis로 교체할 수 있게 경계를 분리한다.

## 11. KPI
- 검색 시작 → 결과 표시 시간

가장 중요한 제품 KPI는 **“빈자리를 실제로 찾는 데 걸린 시간”**이다.

이 프로젝트의 경쟁력은 기능 수가 아니다.
