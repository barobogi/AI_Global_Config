# "빈자리 있어요?" — 도서관/열람실 실시간 좌석 추천 앱 (2탄 최초 기획안 V1)

> 작성: 만복(Planner), 2026-08-30. 65번 뿌리 2탄. GPT-WEB 확장 전 최초 버전 — 처음부터 Lean MVP로 설계(1탄/3탄에서 얻은 교훈 반영, 과설계 금지).

---

## 0. 배경

1탄("오늘뭐하지")·2탄이었던 "주차 어디가?"(3탄으로 순연)에 이은 65번 뿌리 신규 후보. `65_android_apps/Idea/3rd_app_candidates.md`(2026-08-29 Deep Search, odcloud 전체 96,472건 카탈로그 기반)에서 발굴 — 조사한 후보 전체 중 "실시간성 + 규칙기반 적합도"가 가장 높다고 평가됨.

## 1. 한 문장

> **지금 이 순간, 걸어갈 수 있는 거리 안에서 자리 있는 도서관/열람실을 알려주는 앱.**

## 2. 핵심 문제

- 공부/독서하러 도서관 갔다가 자리 없어서 헛걸음하는 경우가 흔함
- 여러 도서관/열람실을 전화나 방문으로 하나씩 확인하는 건 비효율적
- "만석"이라는 정보는 있어도 "그럼 어디가 비어있나"를 종합해서 보여주는 서비스는 드묾

## 3. 핵심 데이터

- **행정안전부 한국지역정보개발원 — 전국 공공도서관 열람실 현황 실시간 정보** (`data.go.kr/data/15142580`, End Point `apis.data.go.kr/B551982/plr_v2`)
- **이미 활용신청 완료**(2026-08-29, 즉시 자동승인, 계정 공용키 동일값 — `API_REGISTRY.md` 참조, 재신청 불필요)
- 제공 필드(추정, Phase 0에서 실측 확인 필요): 도서관명, 열람실명, 총좌석수, 현재이용좌석, 잔여좌석, 좌표

## 4. 킬러 피처 (딱 1개만)

```text
○○도서관 3층 열람실
잔여 12석 / 총 80석
도보 8분
```

성공확률/신뢰도등급/Plan B 같은 부가기능은 넣지 않는다 — "지금 빈자리 몇 개"라는 단일 실시간 수치 하나가 이 앱의 전부다. 1탄의 "성공확률 92%" 같은 복합 스코어링도 여기선 불필요 — 잔여좌석은 그 자체로 이미 명확한 신호라 별도 확률 계산이 군더더기.

## 5. 추천 로직 (순수 규칙기반, 하드필터 + 정렬만)

**입력**: 현재 위치, 최대 도보거리(선택, 기본 15분)

**필터**:
1. 반경 내 도서관만 (하버사인 거리 계산, 1탄 `hard_filter.py` 패턴 재사용 가능)
2. 잔여좌석 0인 곳 제외

**정렬**: 잔여좌석 많은 순 또는 거리 가까운 순 (사용자 토글) — 두 기준 가중합 스코어링은 v1.1로 미룸, v1은 단순 정렬 토글이면 충분

**출력**: 도서관명, 열람실명, 잔여/총좌석, 거리·도보시간, 마지막 데이터 갱신 시각(1탄의 "실시간인 척 안 하기" 원칙 그대로 — Section 15 참조)

## 6. Lean MVP 범위 (v1, Phase 0~1)

```text
Phase 0: B551982 API 실측(응답 필드 확인, 갱신주기 확인 — 지자체별로 다를 수 있음 주의)
Phase 1: FastAPI 단일 서비스(추천 로직 하나) + 로컬 저장
         + Android 2개 화면(위치+반경 입력 → 결과 리스트)
```

**의도적으로 안 넣는 것** (3탄 다이어트에서 배운 교훈 그대로 처음부터 적용):
- 로그인/계정 — 없음
- PostgreSQL/Redis — 없음, 로컬 파일/SQLite로 시작
- 예약/좌석 찜하기 — v1엔 없음(API가 조회 전용이라 애초에 예약 기능 자체가 불가능하기도 함)
- 성공확률 계산, 신뢰도 등급 — 불필요(잔여좌석 자체가 이미 확정 신호)
- 사용자 리뷰/신고 시스템 — v1.1 이후 검토

## 7. 리스크 (Phase 0에서 반드시 확인)

1. **전국 통합 API 갱신주기가 지자체별로 다를 수 있음** — "실시간"이라고 홍보하지만 일부 지자체는 갱신이 느리거나 안 될 가능성. Phase 0에서 여러 지역 실측해서 확인.
2. **좌표 필드 유무** — 거리 계산에 필요한 위경도가 실제로 제공되는지 확인 필요 (없으면 주소→좌표 변환(지오코딩) 별도 필요, 범위 커짐).
3. **KOGL 라이선스 유형** — 상업적 이용 가능 여부 개별 확인 필요(다른 API들처럼 대부분 제1유형일 가능성 높으나 확인 전 확정 금지, `PUBLIC_DATA_STRATEGY.md` 원칙).

## 8. 1탄/3탄에서 이어지는 공통 원칙 (재확인)

- 시크릿은 처음부터 `local.properties`/env, 하드코딩 fallback 금지 (1탄 keystore 사고 교훈)
- 완료보고엔 반드시 `43_function_dev/03_verification_framework/verifiers.py` 실행 로그 첨부
- 문서 수치는 항상 소스 코드와 대조
- Android `debug`/`release` 패키지명 처음부터 분리(`applicationIdSuffix`)

## 9. GPT-WEB에게 기대하는 확장 범위

이 문서는 최초 골격이다. 확장 시 다음을 부탁:
- Section 5 추천 로직을 실제 API 응답 스키마 기준으로 구체화(필드명 확정은 Phase 0 실측 후)
- Android 화면 와이어프레임/컴포넌트 구조 제안
- 장기 로드맵(v1.1 이후: 좌석 예약 연동 가능성이 있는지, 열람실 유형별 필터 등)은 자유롭게 확장해도 좋으나, **v1 범위(Section 6) 자체를 다시 무겁게 만들지 말 것** — 이건 3탄에서 이미 겪은 실수라 반복 안 함.
